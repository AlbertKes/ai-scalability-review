# Scalability Review: wonder-cart-service (prod)
**Date**: 2026-11-20
**Reviewer**: DevOps Engineering Agent

---

## 1. Executive Summary

wonder-cart-service is a critical Tier-1 microservice providing cart lifecycle management, cart item manipulations, and pricing synchronisation across the mobile application, web storefront, and physical point-of-purchase kiosks. Built on the core-ng framework, it coordinates synchronous customer interactions while interacting with downstream services for catalog, pricing, customer profile, and notification updates. The service acts as the central state holder for consumer carts and underpins the core ordering funnel across all customer touchpoints.

Across the 28-day lookback window, the service demonstrated excellent infrastructure health, pristine operational stability, and comfortable resource headroom. HTTP availability and latency Service Level Objectives were fully maintained without any error budget depletion, container restarts, or memory exhaustion events. CPU and memory consumption remained well within provisioned allocation limits with minimal pod scaling activity. Database interactions for the service's own tables operated smoothly with minimal storage footprints, while background asynchronous event processing through Kafka maintained healthy queue throughput.

1. **Shared MySQL Server Slow Query Volume**: The shared database cluster `rfprodv2-flexible-wonder-db` recorded a 28-day daily average of `942.21` slow queries with a single-day spike of `1159`, driven by database-wide activity and representing the primary persistence layer bottleneck.
2. **Unindexed Cart Cleanup Database Scans**: External cleanup message handler `CleanDataMessageHandler` repeatedly scans `carts`, `web_carts`, and `cart_carry_over_histories` by `updated_time` without supporting indexes, forcing sequential full-table scans during batch retention purges.
3. **Shared MySQL Server Replication Lag Spike**: The shared database replica `rfprodv2-flexible-wonder-db-replica-v4` experienced a peak replication lag of `2198.00 s` on 2026-11-02, creating read-staleness risks on the configured read-replica datasource during server-wide heavy write intervals.
4. **Unbounded Cart Item Options Query**: Cart context retrieval in `CartContextService.cartItemOptionMap` queries `cart_menu_item_options` by customer identifier without scoping to the active cart, loading historic option records into JVM memory.
5. **Unindexed Table Scan Suppression in Cart Search**: Back-office search implementations in `CartService.search` and `WebCartService.search` execute unindexed count operations across carts while explicitly calling `Database.suppressSlowSQLWarning(true)` to mask query warnings.

## 6. Recommendations & Action Items

### 1. Add Index on updated_time for Cart Tables (High Priority)
- **Finding**: In `CleanDataMessageHandler` (`backend/wonder-cart-service/src/main/java/app/kafka/CleanDataMessageHandler.java`), batch cleanup queries execute `SELECT id FROM web_carts WHERE updated_time <= ? LIMIT 100`, `SELECT id FROM carts WHERE updated_time <= ? LIMIT 100`, and `SELECT id FROM cart_carry_over_histories WHERE updated_time <= ? LIMIT 100`. None of these three tables have an index on `updated_time` [Source: code → backend/wonder-cart-service/src/main/java/app/wondercart/CartServiceApp.java] [Source: context → code-context.md], causing full-table scans on every batch iteration of 100 rows.
- **Action**: Add Flyway migration scripts creating single-column B-tree indexes on `updated_time` for tables `carts`, `web_carts`, and `cart_carry_over_histories` in `backend/wonder-cart-service/src/main/resources/db/migration/` to eliminate full-table scans during Kafka-triggered cleanup runs with batch size 100 (`CleanDataMessageHandler.BATCH_SIZE = 100`).
- **Owner**: Consumer Backend Team

### 2. Scope Cart Menu Item Options Query by Cart ID (Medium Priority)
- **Finding**: In `CartContextService.cartItemOptionMap` (`backend/wonder-cart-service/src/main/java/app/wondercart/CartContextService.java`), option records are retrieved by executing `cartMenuItemOptionRepository.select()` filtered exclusively by `owner_id = ?` without bounding by cart ID or result limit [Source: context → code-context.md], loading all historic options for the customer into JVM memory before in-memory filtering.
- **Action**: Refactor `CartContextService.cartItemOptionMap` to filter `cart_menu_item_options` by both `owner_id` and the current `cart_id` (or filter by `cart_item_id` list corresponding to active cart items) utilizing the existing composite index `cart_id` on `cart_menu_item_options`.
- **Owner**: Consumer Backend Team

### 3. Eliminate Slow SQL Warning Suppression on Cart Search (Low Priority)
- **Finding**: In `CartService.search` and `WebCartService.search` (`backend/wonder-cart-service/src/main/java/app/wondercart/CartService.java` and `WebCartService.java`), cart search logic executes `cartRepository.select().count()` (full table scan `COUNT(*)`) and joins carts with cart items grouped by owner while invoking `Database.suppressSlowSQLWarning(true)` to silence framework slow query warnings [Source: context → code-context.md].
- **Action**: Remove `Database.suppressSlowSQLWarning(true)` in `CartService` and `WebCartService`, introduce mandatory indexed filters or pagination bounds on queries, and replace unindexed full-table `COUNT(*)` with bounded queries to prevent query latency spikes on back-office paths.
- **Owner**: Consumer Backend Team
