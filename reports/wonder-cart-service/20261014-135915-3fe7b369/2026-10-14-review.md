# Scalability Review: wonder-cart-service (prod)
**Date**: 2026-10-14
**Reviewer**: DevOps Engineering

---

## 1. Executive Summary

wonder-cart-service is a Tier-1 core microservice in the Wonder consumer platform responsible for orchestrating shopping carts across iOS and Android mobile applications, web frontends, and physical Point-of-Purchase kiosks. The service manages cart lifecycle operations including cart creation, item customization, bundle selection, delivery address assignment, tip and payment configuration, and promotional pricing calculation. It serves as the primary coordination layer bridging consumer-facing ordering channels with backend catalog, pricing, customer, and fulfillment systems.

Container runtime health is stable, exhibiting zero process crashes, zero container restarts, and zero memory termination events across the lookback window. Application request execution remains fast with negligible processing latency recorded across all observed percentiles. Error rates remain absent across standard request execution paths, and compute utilization displays significant headroom within current pod allocations. However, the service faces critical architectural risks driven by asynchronous message backlog accumulation, unindexed relational database query patterns, and the absence of fault isolation mechanisms on outbound dependencies.

1. **Kafka Consumer Processing Backlog**: The courier supply health trigger consumer exhibits sustained message backlog with an average lag of 20.75 messages and a peak lag of 232 messages caused by local semaphore concurrency limits and synchronous downstream calls.
2. **Missing Fault Isolation on Critical Path**: Outbound HTTP clients lack circuit breakers and utilize high read timeouts up to 20 seconds, with unconfigured clients defaulting to 60 seconds, risking pod thread starvation during upstream dependency degradation.
3. **Unindexed Database Scans and Filesorts**: High-frequency cart search queries and periodic data cleanup batch tasks execute unindexed full table scans and temporary table filesorts on `carts` and `web_carts`, forcing explicit slow SQL warning suppressions in application code.
4. **Uncoordinated Multi-Pod Background Processing**: Background periodic user synchronization executes fan-out iterations without distributed advisory locking, while concurrency controls rely on in-process semaphores that multiply downstream traffic across scaling replicas.
5. **Table-Locking Deletion Endpoints**: Administrative cart truncation endpoints execute unbounded multi-table deletion queries within open database transactions, creating substantial row lock contention and replication overhead.

## 6. Recommendations & Action Items

### 1. Add Missing Indexes on carts and web_carts Tables (High Priority)
- **Finding**: In `CartService.java` and `WebCartService.java`, cart search queries execute `ORDER BY cart.created_time ASC` with `LEFT JOIN` and `GROUP BY`, forcing temporary tables and unindexed filesorts that require `Database.suppressSlowSQLWarning(true)` to silence alerts. Additionally, in `CleanDataMessageHandler.java`, batch cleanup executes `SELECT id FROM carts WHERE updated_time <= ? LIMIT 100` and `SELECT id FROM web_carts WHERE updated_time <= ? LIMIT 100`, triggering full table scans on every batch iteration across `carts` (39090 rows) and `web_carts` (26466 rows) [Source: MySQL (rfprodv2-flexible-wonder-db/wonder_cart) → SELECT table_name, table_rows, ROUND(data_length/1024/1024,2) AS data_mb, ROUND(index_length/1024/1024,2) AS index_mb, ROUND((data_length+index_length)/1024/1024,2) AS total_mb FROM information_schema.tables WHERE table_schema='wonder_cart' ORDER BY (data_length+index_length) DESC LIMIT 20].
- **Action**: Add Flyway migration scripts creating indexes `idx_carts_created_time (created_time)` and `idx_carts_updated_time (updated_time)` on table `carts`, and matching indexes `idx_web_carts_created_time (created_time)` and `idx_web_carts_updated_time (updated_time)` on table `web_carts`. Remove `Database.suppressSlowSQLWarning(true)` in `CartService.java` and `WebCartService.java` once indexes are applied.
- **Owner**: Consumer Team

### 2. Configure Circuit Breakers and Reduce HTTP Read Timeouts (High Priority)
- **Finding**: In `APIClientModule.java`, all synchronous HTTP clients managed by `CLBConfig` use a 20-second read timeout (`Duration.ofSeconds(20)`), while direct framework clients (`PriceWebService`, `HDRWebService`, `BACycleItemWebService`, `BAGlobalSettingWebService`) have unconfigured timeouts defaulting to 60-second read timeouts. Zero circuit breakers are configured on critical checkout dependencies (`order-service`, `customer-service`, `restaurant-service-v2`, `marketing-service`, `wonder-setting-service`), allowing upstream latency spikes to exhaust HTTP worker thread pools [Source: context → code-context.md].
- **Action**: In `APIClientModule.java`, wrap critical synchronous clients (`PriceWebService`, `PublishedRestaurantWebService`, `PublishedMenuItemWebService`, `PromotionWebService`) with circuit breakers. Reduce the read timeout on `CLBConfig` clients from 20 seconds to 5 seconds (`Duration.ofSeconds(5)`), and explicitly configure `PriceWebService` and `HDRWebService` with `timeout(Duration.ofSeconds(5))` to match the platform 5000 ms standard used in `EnhancedAPIConfig`.
- **Owner**: Consumer Team
