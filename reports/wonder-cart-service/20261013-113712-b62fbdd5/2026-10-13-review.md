# Scalability Review: wonder-cart-service (uat)
**Date**: 2026-10-13
**Reviewer**: Gemini CLI

---

## 1. Executive Summary
The wonder-cart-service is a tier-one microservice responsible for managing mobile, web, and point-of-purchase shopping carts. It handles critical customer-facing transactions such as cart creation, item management, pricing queries, and delivery address configuration. Operating in the consumer domain, the service acts as a primary coordinator that synchronously aggregates data from various downstream services to calculate active cart structures. It serves as an essential gateway in the consumer checkout funnel, making its reliability and scale-out capacity vital for business operations.

During the lookback window, the service exhibited exceptional container-level stability and high performance, maintaining low response latencies for synchronous HTTP endpoints. CPU and memory utilization on the application instances remained extremely low with ample headroom on their allocated resources. No container restarts or memory-related termination events were recorded, indicating a highly stable application runtime environment. However, significant backend bottlenecks were observed in the persistence layer and asynchronous message processing paths, which introduce severe risks of data stale-ness and processing delays.

1. **Critical Database Replication Lag**: The consumer database experiences massive replication delays, peaking at `480 seconds`, which introduces a high risk of serving stale supply and cart information to active users.
2. **Severe Asynchronous Message Consumer Lag**: The `courier-supply-health-trigger-message` topic exhibits severe consumer lag, peaking at `228` messages, which causes significant delays in evaluating courier capacity for active carts.
3. **No Circuit Breakers on Critical Synchronous Paths**: Outbound REST clients lack circuit breakers and explicit timeouts, making the service highly vulnerable to cascading thread pool exhaustion if any core downstream dependency exhibits high latency.
4. **Non-Replica-Safe Local Concurrency Throttle**: The JVM-local semaphore used to throttle courier supply health evaluations scales linearly with the number of replicas, defeating downstream overload protection during scale-out events.
5. **Missing Database Indexes on Foreign Key Columns**: Child tables lack proper database indexes on foreign key columns, causing full table scans during cart load and update flows.

## 6. Recommendations & Action Items

### 1. Implement Circuit Breakers and Explicit Timeouts for Downstream Web Services (High Priority)
- **Finding**: Synchronous user-facing paths make HTTP calls to core downstream systems like `restaurant-service-v2` and `customer-service` without circuit breakers or explicit connect/read timeouts, relying on implicit framework defaults in `CartModule.java` [Source: context → code-context.md]. If any downstream system experiences high latency, the service is vulnerable to thread pool exhaustion.
- **Action**: Modify `CartModule.java` to configure explicit read/connect timeouts of `5000 ms` (reusing the existing timeout configuration used for `PublishedMenuItemWebService` in the same module) and integrate circuit breaker wrappers (such as `lib.clb.CLBConfig` or custom fallbacks) for all critical downstream HTTP clients (e.g. `PublishedRestaurantWebService` and `CustomerWebService`).
- **Owner**: consumer team

### 2. Replace JVM-Local Semaphore with a Distributed Semaphore (High Priority)
- **Finding**: `SemaphoreExecutorUtil.java` uses a standard in-memory `java.util.concurrent.Semaphore` initialized via `app.semaphore.permits` (configured as `5` in dev) to throttle the concurrency of `CourierSupplyHealthTriggerMessageHandler` [Source: context → code-context.md]. Because this semaphore is in JVM-local memory, horizontal scaling to $N$ replicas multiplies the concurrency ceiling to $5 \times N$, defeating the downstream capacity guardrail for `DeliverySupplyService` [Source: context → code-context.md].
- **Action**: Refactor `SemaphoreExecutorUtil.java` to use a distributed semaphore backed by Redis (using Redisson or a similar client library) to enforce a global, replica-safe concurrency limit of `5` across all active pods (reusing the limit value of `5` defined in `app.semaphore.permits`).
- **Owner**: consumer team

### 3. Add Database Indexes on Foreign Key Columns in SQL Migrations (High Priority)
- **Finding**: Table definitions for parent-child associations (e.g., `cart_items` and `cart_menu_item_options`) do not have database indexes configured on foreign key join columns such as `cart_id` or `cart_item_id` in the SQL migrations [Source: context → code-context.md], which causes expensive full table scans during cart load and update flows.
- **Action**: Add explicit indexes on join columns (such as `cart_id` in `cart_items` and `cart_item_id` in `cart_menu_item_options`) in a new Flyway SQL migration script (e.g., `V__add_missing_cart_indexes.sql`) to prevent full table scans and offload the database.
- **Owner**: consumer team

### 4. Parallelize Sequential Outbound HTTP Loop on Cache Misses (Medium Priority)
- **Finding**: In `CourierSupplyHealthDataFetcher.java`, the method `fetchRestaurantInfos(Set<String> restaurantIds)` loops through un-cached restaurant IDs and performs sequential, blocking synchronous REST queries to `publishedRestaurantWebService.getBaseInfo` [Source: context → code-context.md]. This introduces an $O(M)$ sequential delay on cold caches that inflates latency and contributes to Kafka consumer lag on `courier-supply-health-trigger-message` (average lag of `24.36` messages, peak of `228` messages) [Source: Datadog MCP → query_metrics("avg:kafka.consumer_lag{...}")].
- **Action**: Refactor `CourierSupplyHealthDataFetcher.java` to execute outbound HTTP requests in parallel using Java `CompletableFuture` or an executor thread pool, or use a batch retrieval endpoint if supported by `publishedRestaurantWebService`.
- **Owner**: consumer team

### 5. Remove Suppression of Slow SQL Warnings in Cart Services (Medium Priority)
