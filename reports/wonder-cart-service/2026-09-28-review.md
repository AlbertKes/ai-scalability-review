# Scalability Review: wonder-cart-service (uat)
**Date**: 2026-09-28
**Reviewer**: Gemini CLI

## 1. Executive Summary
The `wonder-cart-service` is a Tier-1 microservice responsible for orchestrating shopping carts across multiple user interfaces, including Mobile App, Web, POP, and Back Office operators. It serves as a critical component in the cart modification and checkout preparation lifecycle, handling critical synchronous paths and high-frequency data mutations. The service relies on a MySQL database for persistent storage, a Redis cluster for configuration caching, and Kafka for decoupled background trigger message processing. Its operational stability and responsiveness are critical to the consumer shopping experience and downstream checkout workflows.

The overall infrastructure health observed over the 28-day lookback window is positive, with extremely low latency profiles, zero HTTP error rates, and no container restarts or OOMKill events across all deployments. Pod CPU and memory utilizations are highly stable and operate well within their allocated resource requests and limits. However, significant operational risks exist in the persistent storage layer and client call resilience, primarily characterized by severe replication lag on the shared database and the lack of explicit connection timeouts or circuit breakers on downstream HTTP client integrations.

1. **Severe Database Replication Lag**: The database server exhibits critical replication lag with a 28-day average of `327.93 s` [Source: Datadog MCP → query_metrics("avg:azure.dbformysql_flexibleservers.replication_lag{server_name:ftiuat-flexible-consumer-db}")] and a peak of `1735 s` [Source: Datadog MCP → query_metrics("max:azure.dbformysql_flexibleservers.replication_lag{server_name:ftiuat-flexible-consumer-db}")], delaying data consistency on replica query paths.
2. **Missing Outbound HTTP Connection Timeouts and Circuit Breakers**: Critical downstream API integrations lack explicit connect and read timeouts (relying on framework defaults > 10 s) and circuit breakers [Source: context → code-context.md], exposing the service to cascading thread pool exhaustion.
3. **Non-Replica-Safe Local Semaphore for Throttling**: Concurrency limits in message handling are enforced via a JVM-local semaphore with `5` permits [Source: context → code-context.md], which scales out to `5 * N` under horizontal replicas, bypassing downstream protection.
4. **Shared Database Storage Capacity Saturation**: The shared server `ftiuat-flexible-consumer-db` used storage has reached `490.99 GB` [Source: Azure MCP → get_mysql_flexible_server("ftiuat-flexible-consumer-db")] of `526 GB` [Source: Azure MCP → get_mysql_flexible_server("ftiuat-flexible-consumer-db")] provisioned capacity, which is a major bottleneck although the service's own database `wonder_cart` occupies only `0.05 GB` [Source: MySQL (ftiuat-flexible-consumer-db/wonder_cart) → SELECT table_name, table_rows, ROUND(data_length/1024/1024,2) AS data_mb, ROUND(index_length/1024/1024,2) AS index_mb, ROUND((data_length+index_length)/1024/1024,2) AS total_mb FROM information_schema.tables WHERE table_schema='wonder_cart' ORDER BY (data_length+index_length) DESC LIMIT 20].
5. **Sequential Blocking Downstream API Calls**: Cache misses for restaurant details trigger sequential blocking downstream HTTP calls inside a `for`-loop [Source: context → code-context.md], creating a latent serialization bottleneck.

### 1. Configure Explicit HTTP Client Timeouts and Circuit Breakers (High Priority)
- **Finding**: Outbound HTTP clients (including `PublishedRestaurantWebService`, `CustomerWebService`, `CustomerAddressWebService`, `SearchWebService`, etc.) are declared in `APIClientModule.java` with no explicit read or connect timeouts, nor any circuit breakers or retries, relying implicitly on core.framework library/framework defaults > 10 s [Source: context → code-context.md]. This exposes the service's threads to cascading exhaustion if any downstream dependency degrades.
- **Action**: Add explicit read and connect timeouts (using `Timeout.MILLISECOND_5000` which is 5000 ms, consistent with existing GoogleBot clients configured in `APIClientModule.java`) and register circuit breakers on all critical downstream clients in `APIClientModule.java` [Source: code → infra/uat/app/consumer/kube/resource/22-wonder-cart-service.yml].
- **Owner**: consumer

### 2. Remediate Critical MySQL Replication Lag (High Priority)
- **Finding**: MySQL server replication lag exhibits an average of `327.93 s` [Source: Datadog MCP → query_metrics("avg:azure.dbformysql_flexibleservers.replication_lag{server_name:ftiuat-flexible-consumer-db}")] and peaks at `1735 s` [Source: Datadog MCP → query_metrics("max:azure.dbformysql_flexibleservers.replication_lag{server_name:ftiuat-flexible-consumer-db}")], which severely delays read consistency on paths queried inside `CourierSupplyHealthTriggerMessageHandler` via `replicaDB` repository beans [Source: context → code-context.md].
- **Action**: Coordinate with the platform team to analyze binary logs, investigate query patterns on `ftiuat-flexible-consumer-db-replica-v2` (`infra/uat/app/infra/env/23-mysql-flexible-consumer-server.tf`), and optimize replication performance. Since the server is shared, this affects all schemas on the host.
- **Owner**: platform

### 3. Refactor Sequential HTTP Calls in Courier Supply Health Trigger (Medium Priority)
- **Finding**: In `CourierSupplyHealthDataFetcher.fetchRestaurantInfos`, cache misses for multiple restaurant IDs are resolved by executing synchronous, blocking downstream requests sequentially inside a `for`-loop calling `publishedRestaurantWebService.getBaseInfo` [Source: context → code-context.md], creating a high latency bottleneck.
- **Action**: Refactor `CourierSupplyHealthDataFetcher.fetchRestaurantInfos` to execute parallel HTTP calls using the framework's async dispatching or leverage a bulk-lookup endpoint like `publishedRestaurantWebService.batchGetBaseInfo` to fetch details in a single roundtrip.
- **Owner**: consumer

### 4. Implement Replica-Safe Distributed Throttling (Medium Priority)
- **Finding**: Concurrency limits in `CourierSupplyHealthTriggerMessageHandler` are enforced via a JVM-local semaphore via `SemaphoreExecutorUtil.submitWithSemaphoreFromConfig` with permits controlled by `app.semaphore.permits` defaulting to `5` [Source: context → code-context.md]. This semaphore is not replica-safe; scaling horizontally to `N` replicas multiplies the concurrency limit to `5 * N`, bypassing downstream protection.
- **Action**: Replace the in-memory local semaphore with a distributed lock or semaphore managed via the Redis cluster (`sys.redis.host` [Source: code → infra/uat/app/consumer/kube/resource/22-wonder-cart-service.yml]) or utilize a centralized rate-limiting service to ensure a globally consistent concurrency threshold.
- **Owner**: consumer

### 5. Prevent Shared Database Storage Exhaustion (Medium Priority)
- **Finding**: Shared server `ftiuat-flexible-consumer-db` storage is at `490.99 GB` of `526 GB` provisioned capacity (93.344% saturation) [Source: Azure MCP → get_mysql_flexible_server("ftiuat-flexible-consumer-db")], while the `wonder_cart` database schemas total only `0.05 GB` [Source: MySQL (ftiuat-flexible-consumer-db/wonder_cart) → SELECT table_name, table_rows, ROUND(data_length/1024/1024,2) AS data_mb, ROUND(index_length/1024/1024,2) AS index_mb, ROUND((data_length+index_length)/1024/1024,2) AS total_mb FROM information_schema.tables WHERE table_schema='wonder_cart' ORDER BY (data_length+index_length) DESC LIMIT 20].
- **Action**: Work with the platform team to identify other schemas co-hosted on `ftiuat-flexible-consumer-db` that are driving storage saturation, and establish data pruning or archiving policies to reclaim disk space.
- **Owner**: platform

### 6. Correct Terraform Database Storage Configuration Drift (Low Priority)
- **Finding**: Storage size in `23-mysql-flexible-consumer-server.tf` is configured as `size_gb = 64` [Source: code → infra/uat/app/infra/env/23-mysql-flexible-consumer-server.tf], which has drifted from the live Azure provisioned storage size of `526 GB` [Source: Azure MCP → get_mysql_flexible_server("ftiuat-flexible-consumer-db")].
- **Action**: Update `size_gb` in `23-mysql-flexible-consumer-server.tf` to `526` to match the live Azure resource state and prevent unintended state drift in subsequent Terraform runs.
- **Owner**: platform
