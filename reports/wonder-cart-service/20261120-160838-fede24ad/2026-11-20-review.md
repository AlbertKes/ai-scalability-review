# Scalability Review: wonder-cart-service (prod)
**Date**: 2026-11-20
**Reviewer**: Gemini CLI

---

## 1. Executive Summary
wonder-cart-service is a critical Tier-1 core-ng microservice responsible for cart lifecycle management, item configurations, promotional pricing calculations, and checkout transitions across mobile app, consumer web, and kiosk POP platforms. The service acts as the central shopping session coordinator for all customer orders, persisting active basket state and dispatching synchronization events for downstream delivery supply health evaluation. It exposes high-volume REST endpoints to customer applications while maintaining asynchronous integrations with order, restaurant catalog, and notification domains.

During the twenty-eight-day evaluation window, the service demonstrated outstanding operational stability, flawless availability, and exceptionally low response latencies. Resource utilization across compute and memory remained well within safe operational headroom, with container execution experiencing zero restarts and zero out-of-memory terminations. Kubernetes horizontal pod autoscaling scaled smoothly during peak traffic periods, while Datadog service level objectives maintained near-perfect error budget reserves across all monitored service endpoints.

1. **Shared MySQL Server Slow Query Contention**: The underlying shared database server `rfprodv2-flexible-wonder-db` recorded an elevated daily slow query volume and a peak single-day surge, presenting external contention risk even though `wonder-cart-service` queries execute swiftly.
2. **In-Process Semaphore Concurrency Expansion**: The JVM-local semaphore governing delivery supply health checks multiplies allowed concurrent calls as pod replicas scale out, risking uncoordinated traffic bursts against downstream supply services during peak load.
3. **Full Table Scans in Periodic Cleanup**: Data cleanup operations for expired carts perform queries filtered by updated timestamp without supporting secondary indexes, requiring table scans that will degrade as order history expands.
4. **Unbounded Storage Accumulation in POP Kiosk Carts**: Kiosk point-of-presence cart tables lack automatic expiration or purge routines in the periodic cleanup handler, leading to unpruned record accumulation over time.

## 6. Recommendations & Action Items

### 1. Replace JVM-Local Semaphore with Redis-Backed Concurrency Limiter (High Priority)
- **Finding**: In `SemaphoreExecutorUtil.java`, concurrent execution of `courier-supply-health-trigger-message` tasks is restricted by a static JVM-local `Semaphore` initialized with `app.semaphore.permits = 5` from `conf/prod/resources/app.properties` (read in `src/main/java/app/wondercart/KafkaConsumerModule.java`). When HorizontalPodAutoscaler scales the deployment from 2 to 4 pods (`infra/prod/app/consumer/kube/resource/190-hpa.yml`), aggregate cluster-wide concurrency to downstream delivery supply services expands up to 20 concurrent requests, bypassing intended downstream protection.
- **Action**: Implement a centralized concurrency limiter using the existing Redis cluster via core-ng `Redis` API configured in `src/main/java/app/wondercart/CartModule.java`, or configure `app.semaphore.permits` dynamically based on the active replica count to enforce an aggregate ceiling of 5 concurrent operations across all pods.
- **Owner**: Consumer Team

### 2. Add Secondary Indexes on updated_time for Cleanup Queries (Medium Priority)
- **Finding**: `CleanDataMessageHandler` executes `SELECT id FROM carts WHERE updated_time <= ? LIMIT 100`, `SELECT id FROM web_carts WHERE updated_time <= ? LIMIT 100`, and `SELECT id FROM cart_carry_over_histories WHERE updated_time <= ? LIMIT 100` (`src/main/java/app/wondercart/KafkaConsumerModule.java`). Tables `carts` (43,383 rows), `web_carts` (32,900 rows), and `cart_carry_over_histories` (38,180 rows) have primary keys and owner indexes but lack an index on `updated_time`, causing full table scans during periodic cleanups.
- **Action**: Add secondary index `idx_carts_updated_time (updated_time)` on `carts`, `idx_web_carts_updated_time (updated_time)` on `web_carts`, and `idx_cart_carry_over_histories_updated_time (updated_time)` on `cart_carry_over_histories` via a Flyway database migration script.
- **Owner**: Consumer Team

### 3. Implement Retention Purge for Kiosk POP Cart Tables (Low Priority)
- **Finding**: In `src/main/java/app/wondercart/KafkaConsumerModule.java`, `CleanDataMessageHandler` purges expired mobile app carts (`carts`, `cart_items`) and web consumer carts (`web_carts`, `web_cart_items`), but lacks any deletion logic for kiosk POP cart tables (`pop_carts`, `pop_cart_items`, `pop_cart_menu_item_options`). Although POP tables currently contain only 107 carts (0.06 MB), data accumulates indefinitely without a lifecycle purge policy.
- **Action**: Extend `CleanDataMessageHandler` in `src/main/java/app/wondercart/KafkaConsumerModule.java` to include a batch cleanup task for `pop_carts` and associated child tables using the standard 1-month expiration window applied to mobile and web carts.
