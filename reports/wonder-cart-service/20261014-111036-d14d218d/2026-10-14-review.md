# Scalability Review: wonder-cart-service (prod)
**Date**: 2026-10-14
**Reviewer**: Gemini CLI

---

## 1. Executive Summary
`wonder-cart-service` is a Tier-1 core microservice responsible for consumer shopping cart management across mobile applications (iOS/Android), web platforms, and point-of-purchase (POP) kiosks within the Wonder ecosystem. It provides the critical transactional foundation for basket management, item customization, bundle selection, price calculations, and checkout orchestration. The service interfaces directly with customer ordering flows, mediating interactions between catalog services, pricing engines, promotional systems, and delivery supply health evaluations.

During the 28-day lookback window, the service demonstrated flawless HTTP availability with zero observed errors and zero pod restarts across all deployed instances. Container CPU and memory utilization remained exceptionally low with comfortable headroom below provisioned limits, and application-level latency remained sub-millisecond on median requests. However, critical vulnerabilities exist in dependency resilience, unindexed query execution, Kafka consumer backpressure, and database replication lag that undermine horizontal scalability during peak traffic surges.

1. **Elevated Kafka Consumer Lag on Supply Health Topic**: Consumer lag on topic `courier-supply-health-trigger-message` reached a peak of 232 messages and averaged 43.61 messages due to concurrency bottlenecks in consumer handling.
2. **Missing Circuit Breakers and High Timeouts on Critical Synchronous Dependencies**: Outbound HTTP clients for critical checkout paths lack circuit breakers and rely on 20-second read timeouts or 60-second framework defaults, exposing the service to cascading thread exhaustion.
3. **High Shared MySQL Replication Lag and Daily Slow Queries**: The underlying MySQL database cluster experiences an average replication lag of 340.50 s (peak 397 s) and averages 695.79 slow queries per day across the shared instance.
4. **Unindexed Queries and Forced Slow SQL Suppression in Application Logic**: Critical cart search and cleanup routines lack composite indexes on `created_time` and `updated_time`, triggering full table scans and filesorts masked by programmatic slow SQL warning suppression.
5. **Unconstrained Monolithic Deletions on Core Transactional Tables**: Unbounded table deletion endpoints execute table-wide delete operations in single transactions, risking prolonged row locking and transaction log saturation.

## 6. Recommendations & Action Items

### 1. Implement Circuit Breakers and Explicit Timeout on Critical Path External Services (High Priority)
- **Finding**: In `APIClientModule.java`, synchronous outbound HTTP clients on the critical cart retrieval and checkout path (`PriceWebService` targeting `order-service`, `CustomerWebService`, `PublishedRestaurantWebService`, and `PublishedMenuItemWebService`) lack circuit breakers [Source: context → code-context.md]. Furthermore, `PriceWebService` is bound via `api().client()` with no explicit read timeout, defaulting to core-ng framework default 60s, while CLB clients configure a 20s read timeout (`Duration.ofSeconds(20)`), creating severe thread pool exhaustion risks during upstream latency spikes.
- **Action**: In `APIClientModule.java`, register circuit breakers for `PriceWebService`, `CustomerWebService`, and `PublishedMenuItemWebService`. Reconfigure `PriceWebService` with an explicit read timeout of 5000 ms (`Timeout.MILLISECOND_5000`, the standard timeout already defined in `EnhancedAPIConfig` within this repository) and lower CLB client read timeouts from 20s to 5000 ms to prevent Undertow worker thread starvation.
- **Owner**: Consumer Team

### 2. Add Composite Indexes for Cart Search, Hydration, and Cleanup Queries (High Priority)
- **Finding**: In `CartService.java` (`search`), `WebCartService.java` (`search`), and `CleanDataMessageHandler.java`, queries execute unindexed filesorts and full table scans. Specifically, `carts` and `web_carts` are queried with `ORDER BY created_time ASC` and filtered in cleanup with `WHERE updated_time <= ?`, yet neither table contains an index on `created_time` or `updated_time` (only `PRIMARY KEY` on `id` and `UNIQUE KEY` on `owner_id` exist in schema) [Source: context → code-context.md] [Source: MySQL (rfprodv2-flexible-wonder-db/wonder_cart) → SELECT table_name, table_rows, ROUND(data_length/1024/1024,2) AS data_mb, ROUND(index_length/1024/1024,2) AS index_mb, ROUND((data_length+index_length)/1024/1024,2) AS total_mb FROM information_schema.tables WHERE table_schema='wonder_cart' ORDER BY (data_length+index_length) DESC LIMIT 20]. This forced developers to add `Database.suppressSlowSQLWarning(true)` in application code to mask slow query warnings.
- **Action**: Add Flyway migration scripts creating composite index `idx_carts_created_time (created_time)` and `idx_carts_updated_time (updated_time)` on `carts` and `web_carts`. Additionally, add index `idx_cart_items_cart_created (cart_id, created_time)` on `cart_items` to eliminate filesorts during `CartContextService.java` item hydration, and remove `Database.suppressSlowSQLWarning` calls.
- **Owner**: Consumer Team

### 3. Scale Kafka Concurrency and Address Consumer Lag for Supply Health Trigger (High Priority)
- **Finding**: Topic `courier-supply-health-trigger-message` exhibits average consumer lag of 43.61 messages and peak lag of 232 messages [Source: Datadog MCP → query_metrics("max:kafka.consumer_lag{env:prod,consumer_group:wonder-cart-service} by {topic}.rollup(max, 86400)")]. In `KafkaConsumerModule.java`, consumer concurrency is bound to `CommonConfig.CONCURRENCY` and execution within `CourierSupplyHealthTriggerMessageHandler.java` is restricted by a static JVM semaphore of 5 permits (`app.semaphore.permits=5` in `app.properties`) [Source: context → code-context.md], which bottlenecks throughput.
- **Action**: In `KafkaConsumerModule.java` and `app.properties`, decouple topic `courier-supply-health-trigger-message` concurrency from other topics, increase `app.semaphore.permits` from 5 to 15, or transition from an in-process Java Semaphore to a distributed rate limiter, and tune Kafka consumer partition concurrency to eliminate lag.
- **Owner**: Consumer Team

### 4. Replace Non-Atomic Redis Rate Limiting with Atomic SETNX in Message Handlers (Medium Priority)
- **Finding**: In `CourierSupplyHealthTriggerMessageHandler.java`, message deduplication performs a sequential `redis.get()` followed by `redis.set(..., Duration.ofSeconds(duration))` [Source: context → code-context.md]. ### 6. Add Distributed Lock to Periodic Online User Supply Health Processor (Medium Priority)
