# Scalability Review: wonder-cart-service (prod)
**Date**: 2026-11-20
**Reviewer**: DevOps Engineer

---

## 1. Executive Summary

wonder-cart-service is a tier-1 core microservice responsible for cart lifecycle management across Wonder mobile, web, and point-of-purchase client channels. The service orchestrates cart creation, item additions, bundle choices, promotions, pricing coordination, and background synchronization with courier supply systems. It operates in the prod-consumer namespace as a stateless core-ng Java application with dedicated deployment variants for synchronous API traffic and asynchronous event processing.

Across the 28-day lookback window, the service exhibited excellent operational stability, ultra-low latencies, zero application errors, and healthy resource headroom. Resource utilization remains low relative to provisioned pod limits, with CPU and memory operating well within configured boundaries and no container restart or OOMKill events recorded. Both latency and availability Service Level Objectives were fully maintained throughout the period. The primary areas requiring attention involve unindexed table queries during background data cleanup, slow query warning suppression on search endpoints, and shared persistence layer monitoring.

1. **Unindexed Table Scans in Cleanup Handlers**: `CleanDataMessageHandler` executes batch deletion queries against `carts`, `web_carts`, and `cart_carry_over_histories` that perform repeated full table scans due to missing indexes on `updated_time`.
2. **Slow Query Suppression in Search Endpoints**: `CartService.search()` and `WebCartService.search()` execute unindexed full table scans and explicitly invoke `Database.suppressSlowSQLWarning(true)` to silence slow query alerts.
3. **Sequential Downstream RPCs in Courier Health Fetcher**: `CourierSupplyHealthDataFetcher.fetchRestaurantInfos()` issues sequential individual HTTP requests to `restaurant-service` on cache miss rather than utilizing bulk retrieval.
4. **Elevated Shared MySQL Slow Query Volume**: The shared MySQL server `rfprodv2-flexible-wonder-db` recorded a daily average of 942.21 slow queries and a single-day peak of 1159 slow queries [Source: Datadog API → query-metrics("sum:azure.dbformysql_flexibleservers.slow_queries{name:rfprodv2-flexible-wonder-db}.as_count().rollup(sum, 86400)")].
5. **Shared MySQL Replication Lag Spike**: The shared MySQL server recorded a peak replication lag of 2198.00 s on 2026-11-02 [Source: Datadog API → query-metrics("max:azure.dbformysql_flexibleservers.replication_lag{name:rfprodv2-flexible-wonder-db-*}.rollup(max, 86400)")], which serves as a shared infrastructure reminder for the database owning team.
