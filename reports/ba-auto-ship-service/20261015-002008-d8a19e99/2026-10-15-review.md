# Scalability Review: ba-auto-ship-service (prod)
**Date**: 2026-10-15
**Reviewer**: DevOps Engineer

---

## 1. Executive Summary

ba-auto-ship-service is a tier-one core subscription and order automation engine within the Blue Apron consumer architecture. The service manages the end-to-end subscriber lifecycle, including weekly auto-ship cart generation, recipe customization, cutoff enforcement, payment pre-authorization, and order submission to downstream order management and fulfillment systems. It operates as a multi-workload deployment composed of a customer-facing REST API service, an asynchronous background task worker handling Kafka event streams, and an isolated offline assignment simulation runner.

During the lookback window, the service maintained operational stability with no container restarts, no memory-induced pod terminations, and a low baseline error rate. Core synchronous request latencies remained healthy during regular operations, while pod CPU and memory utilization stayed within provisioned cluster allocations. However, significant scalability bottlenecks exist in the persistence and integration layers, driven by massive database table growth, unindexed aggregations, cascading failure vulnerabilities from unconfigured downstream HTTP client timeouts, and high peak asynchronous message lag.

1. **Massive Database Table Accumulation**: The `auto_ship_cart_fulfillment_events` table has grown to `37.77 GB` with `1381162` rows, exceeding the 10 GB scalability threshold without an automated data archival or partitioning lifecycle.
2. **Cascading Failure Risk from Unbounded HTTP Client Timeouts**: Critical downstream dependencies, including order and inventory web services, lack circuit breakers and fall back to the framework default 25-second timeout, risking thread pool exhaustion.
3. **Elevated Kafka Consumer Lag During Peak Processing**: Peak asynchronous consumer lag reached `1944` messages on the `auto-ship-rebalance-event-message` topic due to single-threaded consumer concurrency and synchronous database transaction overhead.
4. **Elevated MySQL Replication Lag and Unindexed Scans**: Replication lag averaged `18.50 s` with a peak of `27 s`, aggravated by parallel unindexed `STRAIGHT_JOIN` queries scanning multi-million-row cart tables.
5. **Atlas MongoDB Secondary Query Scan Inefficiencies**: Atlas MongoDB recorded a peak query targeting ratio of `8333.82` and a peak read latency of `247.88 ms` on 2026-09-24, reflecting unindexed secondary scans during batch operations.

## 6. Recommendations & Action Items

### 1. Implement Data Archival and Partitioning for Fulfillment Events (High Priority)
- **Finding**: Table `auto_ship_cart_fulfillment_events` managed by `AutoShipCartFulfillmentEventService` has grown to `37.77 GB` (36,053.02 MB data and 2,618.56 MB index across 1,381,162 rows) [Source: MySQL (rfprodv2-ba-consumer-db/ba_auto_ship) → SELECT table_name, table_rows, ROUND(data_length/1024/1024,2) AS data_mb, ROUND(index_length/1024/1024,2) AS index_mb, ROUND((data_length+index_length)/1024/1024,2) AS total_mb FROM information_schema.tables WHERE table_schema='ba_auto_ship' ORDER BY (data_length+index_length) DESC LIMIT 20], exceeding the 10 GB scalability threshold and driving MySQL replica lag to an average of `18.50 s` [Source: Datadog MCP → query_metrics("max:azure.dbformysql_flexibleservers.replication_lag{name:rfprodv2-ba-consumer-db-*}.rollup(max, 86400)")].
- **Action**: Implement a scheduled retention pruning job or MySQL RANGE partitioning by month/cycle for `auto_ship_cart_fulfillment_events` to purge or archive completed event payloads older than 90 days, bringing table size below the 10 GB threshold.
- **Owner**: Data Engineering / BA Consumer Backend Team

### 2. Configure Explicit HTTP Timeouts and Circuit Breakers on Critical External APIs (High Priority)
- **Finding**: A total of 35 outbound WebService interfaces in `APIClientModule.java`, including `BAOrderWebService`, `PriceWebService`, `OrderWebService` (`app.order.serviceURL`), and `MenuItemInventoryWebService` (`app.baInventory.serviceURL`), lack custom timeout configurations and circuit breakers, falling back to Core-NG framework defaults of 25 seconds and 3 retries [Source: context → code-context.md].
- **Action**: Register `BAOrderWebService`, `PriceWebService`, `OrderWebService`, `MenuItemInventoryWebService`, and `PaymentServiceProviderSelectorWebService` via `EnhancedAPIModule` with explicit 1,500 ms timeouts (matching existing sibling configurations for `CustomerWebService` and `FRFulfillmentWebService` in `APIClientModule.java`) and wire fallback circuit breakers.
- **Owner**: BA Consumer Backend Team

### 3. Eliminate Row Lock Contention on Batch Completion Counters (High Priority)
- **Finding**: `AutoShipAuthCartTaskService.authCart` and `AutoShipGenerateOrderTaskService.generateOrder` execute concurrent counter updates `UPDATE auto_ship_auth_cart_task_batches SET completed_task = completed_task + 1 WHERE id = ?` and `UPDATE auto_ship_generate_order_task_batches SET completed_task = completed_task + 1 WHERE id = ?` across 800 to 1,000 tasks per batch without row lock sequencing [Source: context → code-context.md], causing high lock wait contention on parent batch rows.
- **Action**: Refactor completion tracking to aggregate counters in Redis via atomic increments or adopt the `SELECT ... FOR UPDATE` row locking pattern established in `BAAutoShipRebalanceEventMessageHandler.java:103`, updating MySQL batch progress at periodic intervals rather than on each individual task.
- **Owner**: BA Consumer Backend Team

### 4. Enable Redis Cache Fallback and Graceful Lock Handling in Production (Medium Priority)
- **Finding**: Production configuration in `conf/prod/resources/app.properties` explicitly disables Redis cache fallback with `app.redisCacheFallback.enabled=false`, and `AutoShipRedisLockService.tryLock` returns false on connection failure [Source: context → code-context.md], which will cause all subscriber plan updates, cart confirmations, and address updates to fail with HTTP 409 Conflict during Redis disruptions.
- **Action**: Set `app.redisCacheFallback.enabled=true` in `conf/prod/resources/app.properties` to activate `FallbackCacheStore` during Redis outages, and implement retry logic in `AutoShipRedisLockService.tryLock` to prevent abrupt request rejections.
- **Owner**: DevOps / BA Consumer Backend Team

### 5. Increase Kafka Consumer Concurrency for Batch and Rebalance Topics (Medium Priority)
- **Finding**: Peak consumer lag reached `1944` messages on topic `auto-ship-rebalance-event-message` [Source: Datadog MCP → query_metrics("max:kafka.consumer_lag{env:prod,consumer_group:ba-auto-ship-service} by {topic}.rollup(max, 86400)")]. Concurrency is hardcoded to 1 for `task.rebalanceEvent.KafkaConcurrency`, `task.authCart.KafkaConcurrency`, and `task.generateOrder.KafkaConcurrency` in `MessageSubscribeModule.java`, creating a single-worker bottleneck during batch processing.
- **Action**: Increase Kafka partition count and consumer concurrency from 1 to 3 for `auto-ship-rebalance-event-message`, `ba-auto-ship-auth-cart-message`, and `ba-auto-ship-generate-order-message` in `MessageSubscribeModule.java`, matching the concurrency of 3 configured for the sibling `notification` and `customer-auto-ship-event` groups.
- **Owner**: BA Consumer Backend Team

### 6. Optimize Heavy STRAIGHT_JOIN Reporting Queries and Suppressed Scans (Medium Priority)
- **Finding**: `BOBAAutoShipCartItemQueryService.cartItemStatistics` runs 4 parallel `STRAIGHT_JOIN` queries across `auto_ship_carts` (1,376,051 rows) and `auto_ship_cart_items` (1,979,941 rows) without multi-column covering indexes, while `BAAutoShipMigrationService.getUnviewedQuantity` explicitly wraps an unindexed join with `Database.suppressSlowSQLWarning(true)` [Source: context → code-context.md], contributing to MySQL replica lag averaging `18.50 s` [Source: Datadog MCP → query_metrics("max:azure.dbformysql_flexibleservers.replication_lag{name:rfprodv2-ba-consumer-db-*}.rollup(max, 86400)")].
- **Action**: Add composite indexes on `auto_ship_carts (cycle_id, status, viewed, item_build_type)` and `auto_ship_cart_items (auto_ship_cart_id, menu_item_id, fulfillment_center_code)`, and pre-calculate cycle-level demand statistics asynchronously into `customer_ba_subtotals_and_savings` or Redis.
- **Owner**: BA Consumer Backend Team

### 7. Expand HPA Maximum Replicas for Traffic Burst Headroom (Low Priority)
- **Finding**: In `infra/prod/app/baconsumer/kube/resource/110-hpa.yml`, HPA is configured with `minReplicas: 3` and `maxReplicas: 5`. Average replica count is `3.00` and peak replica count reached `4` [Source: Datadog MCP → query_metrics("avg:kubernetes_state.deployment.replicas{env:prod,kube_deployment:ba-auto-ship-service}.rollup(avg, 86400)") & query_metrics("max:kubernetes_state.deployment.replicas{env:prod,kube_deployment:ba-auto-ship-service}.rollup(max, 86400)")], yielding scaling headroom `(5 - 3.00) / 5 = 40.00%` (YELLOW threshold 25% – 50%) and leaving only 1 replica of headroom during 6.19x peak traffic surges.
- **Action**: Increase `maxReplicas` from 5 to 8 in `infra/prod/app/baconsumer/kube/resource/110-hpa.yml`, raising scaling headroom to `(8 - 3.00) / 8 = 62.50%` to comfortably handle projected +1Q and +2Q surge loads without pod exhaustion.
- **Owner**: DevOps / BA Consumer Backend Team
