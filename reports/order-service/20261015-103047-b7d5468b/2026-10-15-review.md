# Scalability Review: order-service (prod)
**Date**: 2026-10-15
**Reviewer**: DevOps Engineer

---

## 1. Executive Summary
`order-service` is a Tier-1 core microservice responsible for orchestrating the end-to-end customer ordering lifecycle, shopping cart price calculations, delivery time slot reservations, and kitchen order placement across both internal culinary operations and third-party marketplace channels. Built on Java and the Core-NG framework, it serves as the central transaction hub for consumer mobile and web applications, coordinating downstream integrations with payment processing, kitchen management, menu pricing, tax calculation, and customer communication services. Because any disruption directly impacts revenue generation and order fulfillment, high availability, resilience, and operational scalability are paramount.

Across the 28-day observation period, the service demonstrated excellent application runtime stability with zero container restarts, zero out-of-memory events, and an exceptionally low HTTP error rate across tens of millions of incoming requests. Core API latency remained consistently low for the vast majority of operations, and pod memory working sets stayed comfortably beneath allocated container limits. However, the service faces substantial scalability risks in its persistence layer due to severe slow query accumulation and prolonged replication lag on the shared relational database, extensive accumulation of unarchived historical table data, and an absence of horizontal pod autoscaling combined with pod CPU requests configured below average operational consumption. Furthermore, critical synchronous external dependencies lack automated circuit breakers and granular request timeouts, leaving incoming worker threads vulnerable to downstream latency brownouts.

1. **Missing Circuit Breakers and Explicit Timeouts on Downstream Synchronous RPCs**: Critical checkout and pricing endpoints synchronously depend on external services via `OrderServiceApp.java` where 55+ client interfaces lack granular timeouts and zero circuit breakers are configured, exposing request threads to cascading exhaustion during downstream outages.
2. **Persistence Layer Saturation and Massive Unarchived Table Accumulation**: MySQL database `rfprodv2-flexible-wonder-db/order` experiences severe slow query activity averaging `689.50` queries per day [Source: Datadog MCP → query_metrics("sum:azure.dbformysql_flexibleservers.slow_queries{name:rfprodv2-flexible-wonder-db}.as_count().rollup(sum, 86400)")], replication lag peaking at `397 s` [Source: Datadog MCP → query_metrics("max:azure.dbformysql_flexibleservers.replication_lag{name:rfprodv2-flexible-wonder-db-*}.rollup(max, 86400)")], and 16 tables exceeding 10 GB led by `order_timelines_v2` at `253.62 GB` [Source: MySQL (rfprodv2-flexible-wonder-db/order) → SELECT table_name, table_rows, ROUND(data_length/1024/1024,2) AS data_mb, ROUND(index_length/1024/1024,2) AS index_mb, ROUND((data_length+index_length)/1024/1024,2) AS total_mb FROM information_schema.tables WHERE table_schema='order' ORDER BY (data_length+index_length) DESC LIMIT 20].
3. **Stateless Service Lacks Horizontal Pod Autoscaling While CPU Requests Are Underprovisioned**: In `15-order-service.yml`, the service runs with a static replica count of `3` and CPU request of `100m` (`0.1 cores`), while average CPU usage of `0.1055 cores` already exceeds the request at `105.5%` [Source: Datadog MCP → query_metrics("avg:kubernetes.cpu.usage.total{env:prod,service:order-service}.rollup(avg, 86400)")] and peak CPU reaches `2.3368 cores` [Source: Datadog MCP → query_metrics("max:kubernetes.cpu.usage.total{env:prod,service:order-service}.rollup(max, 86400)")].
4. **Permanent Order Deadlock Vulnerability on Pod Termination**: In `OrderOperationSyncService.java`, distributed locking inserts unexpired rows into MySQL table `order_operation_locks` without a time-to-live or lease expiration mechanism, causing any unexpected pod restart or failure while holding a lock to permanently block all subsequent operations on that order.
5. **Elevated Kafka Consumer Lag on Asynchronous Integration Topics**: Consumer group `order-service` exhibits elevated 28-day average lag on fulfillment package events (`21.3` messages, peak `62` messages) and tax report events (`15.6` messages, peak `50` messages) [Source: Datadog MCP → query_metrics("max:kafka.consumer_lag{env:prod,consumer_group:order-service} by {topic}.rollup(max, 86400)")], exceeding healthy processing thresholds.

## 6. Recommendations & Action Items

### 1. Outbound HTTP Client Timeouts on Critical Synchronous Dependencies (High Priority)
- **Finding**: In `OrderServiceApp.java`, 55+ outbound WebService client interfaces (including `PaymentWebService`, `PromotionWebService`, `HDRPlanningWebService`, `CustomerWebService`, and `CustomerWalletWebService`) are registered without explicit timeouts, falling back to Core-NG's 60-second read timeout default. In contrast, sibling clients like `ItemWebService` and `TaxWebService` in the same class explicitly configure a 2000 ms connect timeout and 2000 ms / 1000 ms read timeout.
- **Action**: Update `OrderServiceApp.java` to explicitly configure HTTP client timeouts on `PaymentWebService`, `PromotionWebService`, `HDRPlanningWebService`, `CustomerWebService`, and `CustomerWalletWebService` using the codebase's established standard of 2000 ms connect timeout and 2000 ms read timeout (matching `ItemWebService`).

### 2. Distributed Lock Lease Expiration and Automatic Cleanup (High Priority)
