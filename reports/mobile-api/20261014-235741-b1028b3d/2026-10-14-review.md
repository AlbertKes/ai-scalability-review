# Scalability Review: mobile-api (prod)
**Date**: 2026-10-14
**Reviewer**: DevOps Engineer

---

## 1. Executive Summary
The `mobile-api` service operates as a Tier-1 Backend-for-Frontend (BFF) and API aggregation gateway for the consumer mobile applications across iOS and Android platforms. It exposes the primary synchronous user journeys encompassing session initialization, restaurant and dish discovery, cart management, checkout orchestration, and real-time order tracking. As the front-line aggregation layer for all customer-facing mobile interactions, any degradation or failure within this service directly halts consumer order placement and impairs customer account access.

During the 28-day lookback window, the service demonstrated consistent operational stability with zero container restarts and zero out-of-memory events across all deployed pods. Web traffic error rates remained minimal, and baseline compute utilization showed comfortable headroom against container resource requests. However, the service exhibits critical latency degradation driven by long outbound client timeouts and a complete absence of circuit breaker state machines on synchronous downstream dependencies. Furthermore, the underlying MySQL persistence layer displays severe replication lag and persistent slow query execution on the shared database cluster, presenting immediate reliability risks during traffic surges.

1. **Absence of Circuit Breakers and Excessive Dependency Timeouts**: The service lacks circuit breaker protection across all critical paths, allowing external client timeouts up to 20000 ms to exhaust Undertow worker threads during downstream degradation.
2. **Persistence Layer Degradation with Severe Replication Lag**: The shared MySQL cluster exhibits high replication lag peaking at 397 seconds and substantial slow queries, creating severe read consistency risks.
3. **Elevated Tail Latency on Core Endpoints**: Average P95 latency of 622.57 ms and average P99 latency of 1542.34 ms exceed acceptable interactive thresholds for a Tier-1 gateway.
4. **Disabled Kafka Consumers Causing Stale Configuration**: The Kafka consumer module remains disabled across all deployment environments, preventing event-driven cache invalidation and forcing prolonged cache lifetimes.
5. **Peak CPU Surges Narrowing Container Headroom**: Peak CPU usage reached 2.856 cores (71.40% of the 4 cores limit), diminishing compute headroom during burst periods.

## 6. Recommendations & Action Items

### 1. Implement Circuit Breakers and Reduce Downstream Client Timeouts (High Priority)
- **Finding**: In `AppCartWebService`, `OrderWebService.placeOrderV2`, `GrubhubRestaurantWebService`, and `GrubhubOrderWebService` [Source: code → frontend/mobile-api/src/main/java/com/wonder/mobile/order/OrderModule.java], HTTP clients configure read timeouts between 15000 ms and 20000 ms with 2 retries, without circuit breaker state machines [Source: context → code-context.md]. Average P95 latency is 622.57 ms [Source: Datadog MCP → query_metrics("p95:trace.undertow_http.request{env:prod,service:mobile-api}.rollup(avg, 86400)")] and average P99 latency is 1542.34 ms [Source: Datadog MCP → query_metrics("p99:trace.undertow_http.request{env:prod,service:mobile-api}.rollup(avg, 86400)")]. Under downstream degradation, Undertow worker threads remain blocked for 30000 ms to 60000 ms, risking worker thread pool saturation.
- **Action**: Implement circuit breakers with fast-fail capability on `OrderWebService` and `GrubhubOrderWebService` interfaces, and reduce downstream read timeouts from 15000 ms / 20000 ms to 5000 ms, matching the standard timeout established for `CustomerMembershipWebService` [Source: context → code-context.md].
- **Owner**: Consumer Team

### 2. Add Query Pagination and Optimize `sessions` Table Access (High Priority)
- **Finding**: In `MigrateNonCityAddressService.java` [Source: code → frontend/mobile-api/src/main/java/com/wonder/mobile/migration/service/MigrateNonCityAddressService.java], `sessionRepository.select().where("address_id IS NULL").where("city IS NULL").where("state IS NOT NULL").fetch()` performs an unbounded table scan against the `sessions` table (2,112,802 rows, 2666.83 MB total storage) [Source: MySQL (rfprodv2-flexible-wonder-db/mobile) → SELECT table_name, table_rows, ROUND(data_length/1024/1024,2) AS data_mb, ROUND(index_length/1024/1024,2) AS index_mb, ROUND((data_length+index_length)/1024/1024,2) AS total_mb FROM information_schema.tables WHERE table_schema='mobile' ORDER BY (data_length+index_length) DESC LIMIT 20]. Additionally, `CustomerUpdatedMessageHandler.java` and `WonderSpotService.java` explicitly invoke `Database.suppressSlowSQLWarning(true)` on `sessions` lookups [Source: context → code-context.md].
- **Action**: Add explicit batch pagination with `limit(300)` (matching the batch size standard in `MigrateLoginHistoryController.java`) to `MigrateNonCityAddressService.java`, remove `Database.suppressSlowSQLWarning(true)` calls, and optimize the composite index `ix_sessions_user_id_expired_time` to prevent slow table scans.
- **Owner**: Consumer Team

### 3. Activate Dedicated Kafka Consumer Deployment for Event-Driven Invalidation (Medium Priority)
- **Finding**: In `conf/prod/resources/app.properties` [Source: context → code-context.md; infra/prod/app/consumer/kube/resource/kafka-consumer/55-mobile-api-kafka-consumer.yml], `app.enableKafkaConsumer` is set to `false`, disabling all 11 event handlers in `KafkaConsumerModule` (including `ConsumerDeliveryZoneUpdatedMessage`, `CustomerUpdatedMessage`, and `WhitelistChangedMessage`). As a consequence, pods cannot invalidate stale cache entries reactively, relying instead on 12-hour to 24-hour TTL expiration.
- **Action**: Enable `APP_ENABLEKAFKACONSUMER=true` specifically on the isolated `mobile-api-kafka-consumer` deployment (where it is already declared in the container environment manifest) while maintaining consumers disabled on user-facing web pods, enabling event-driven cache invalidation without impacting interactive web traffic.
- **Owner**: Consumer Team

### 4. Migrate Pod-Local Delivery Zone Cache to Distributed Redis (Medium Priority)
- **Finding**: In `DeliveryZoneService.java` [Source: code → frontend/mobile-api/src/main/java/com/wonder/mobile/zone/service/DeliveryZoneService.java], `localCacheStore` caches delivery zone names in JVM heap memory with a 30-minute eviction interval. Because local memory state is isolated to each pod and not synchronized across replicas, pods serve inconsistent zone metadata during updates.
- **Action**: Migrate `DeliveryZoneService.localCacheStore` to the existing distributed Redis cache infrastructure using `cache().add(...)`, applying a 30-minute TTL and reusing the established `redis.timeout` configuration.
